# eNSP 自动故障实验复现步骤

本说明适用于当前集成实验机、`feat/midterm-integration` 分支，以及已配置的 R1-R2-R3 拓扑。
先复现路由缺失实验，再按需复现接口关闭实验。

## 1. 区分两个命令窗口

- eNSP 路由器窗口：出现 `<R1>`、`<R2>` 或 `[R2]`，只能输入 VRP 网络设备命令。
- Windows PowerShell：出现 `PS C:\...>`，用来输入本说明中的 Python 命令。

不要把 Python 命令输入路由器窗口。自动实验运行期间，不要同时在路由器窗口输入命令，也不要停止节点或保存故障状态。

## 2. 启动并检查拓扑

以管理员身份启动 eNSP，打开之前验证过的集成拓扑，启动 R1、R2、R3。
等待三个设备完成启动，命令行能显示设备提示符。

如果再次出现已确认由 MessageTransfer 引起的错误 40，在管理员 PowerShell 中执行：

```powershell
sc.exe stop MessageTransfer
```

然后重新启动设备。设备已正常启动时不必重复操作。

在 R1 的 eNSP 命令窗口输入：

```text
return
ping 192.168.3.1
```

应当能收到回复。理想结果是 `0.00% packet loss`。首次有少量丢包可再检查一次；如果一直 100% 丢包，先排查正常网络，不要继续注入故障。

本次路由缺失实验删除的是 R2 的静态路由，不是 R1 的路由：

```text
ip route-static 192.168.3.0 255.255.255.0 10.0.23.2
```

## 3. 进入项目目录

打开 Windows PowerShell，输入：

```powershell
Set-Location 'C:\Users\23044\Desktop\person\大创\netpath-doctor'
git status --short --branch
```

当前实验版本应为 `feat/midterm-integration`。如果显示其他分支，先确认代码版本，不要直接覆盖未提交修改。

本机已有 `.venv` 和 `config/ensp_console.local.json`，不需要重新创建。
程序通过本地 Console 连接 R1、R2、R3，端口分别是 2000、2001、2002。

设置本次实验的报告编号，避免覆盖之前的实验记录：

```powershell
$runTag = Get-Date -Format 'yyyyMMdd_HHmmss'
```

后续命令均在同一个 PowerShell 窗口执行。多行命令末尾的反引号是 PowerShell 续行符，复制时保留，后面不要添加空格。

## 4. 检查程序能否连接三台设备

```powershell
.\.venv\Scripts\python.exe -m benchmarks.live_preflight `
  --transport ensp-console `
  --devices config/ensp_console.local.json `
  --output "reports/live/console_preflight_$runTag.json" `
  --raw-output-dir "reports/live/console_preflight_${runTag}_raw"
```

通过标准：

```json
{
  "total": 3,
  "reachable": 3,
  "failed": 0,
  "all_reachable": true
}
```

这里的 reachable 表示程序能读取设备 CLI，不代表业务目标一定能 ping 通。
如果不是 3/3，先检查设备是否启动完成、是否打开正确拓扑、Console 端口是否与本地配置一致。

## 5. 先运行一次路由缺失实验

```powershell
.\.venv\Scripts\python.exe -m benchmarks.live_experiment `
  scenarios/live/case_002_route_missing.example.json `
  --transport ensp-console `
  --devices config/ensp_console.local.json `
  --fault-type ROUTE_MISSING `
  --trials 1 `
  --output "reports/live/console_route_missing_${runTag}_trial.json" `
  --raw-output-dir "reports/live/console_route_missing_${runTag}_trial_raw"
```

程序自动执行以下流程，不需要手动 shutdown 或删除路由：

1. 从 R1 ping 192.168.3.1，确认故障前网络可达。
2. 查询 R2 的目标路由，确认原路由存在。
3. 在 R2 执行删除静态路由的配置命令。
4. 验证 R2 不再有覆盖目标 IP 的路由。
5. Agent 执行诊断命令，Parser 将真实输出转换为事实，规则状态机得出诊断。
6. 实验控制器在 finally 路径中恢复路由，并查询验证。
7. 从 R1 再次 ping 目标，确认业务连通性恢复。

ping 和 tracert 需要等待设备回显，运行时可能暂时没有终端输出。不要反复启动同一个实验，也不要强制终止进程。

成功时，报告开头应包含：

```json
{
  "requested_trials": 1,
  "passed_trials": 1,
  "all_passed": true
}
```

还应检查 trial 内的 `diagnosis`：`diagnosis_status=COMPLETED`、`fault_device=R2`、`fault_type=ROUTE_MISSING`。
`recovery.success` 应为 true，`post_recovery.facts.reachable` 应为 true。

## 6. 单次通过后，连续运行三次

```powershell
.\.venv\Scripts\python.exe -m benchmarks.live_experiment `
  scenarios/live/case_002_route_missing.example.json `
  --transport ensp-console `
  --devices config/ensp_console.local.json `
  --fault-type ROUTE_MISSING `
  --trials 3 `
  --output "reports/live/console_route_missing_${runTag}_three.json" `
  --raw-output-dir "reports/live/console_route_missing_${runTag}_three_raw"
```

成功标准：`requested_trials=3`、`passed_trials=3`、`all_passed=true`。
每轮都应正确诊断，并恢复路由和连通性。三次通过只说明此版本在这个拓扑上的三次实验成功，不代表所有网络都已验证。

## 7. 查看自己的实验结果

在同一个 PowerShell 中输入：

```powershell
$report = Get-Content "reports/live/console_route_missing_${runTag}_three.json" -Raw -Encoding UTF8 | ConvertFrom-Json
$report | Select-Object requested_trials, passed_trials, all_passed
$report.trials | ForEach-Object {
  [pscustomobject]@{
    Passed = $_.passed
    Status = $_.diagnosis.diagnosis_status
    Device = $_.diagnosis.fault_device
    Fault = $_.diagnosis.fault_type
    Recovery = $_.recovery.success
    Reachable = $_.post_recovery.facts.reachable
    PacketLoss = $_.post_recovery.facts.packet_loss
  }
} | Format-Table -AutoSize
```

原始设备回显位于本次报告对应的 `_raw` 目录。
答辩录像可以展示拓扑、执行命令、诊断结果和恢复结果。报告与原始回显须对应同一次运行。

## 8. 可选：复现接口关闭实验

路由缺失实验结束、网络恢复后，执行：

```powershell
.\.venv\Scripts\python.exe -m benchmarks.live_experiment `
  scenarios/live/case_001_interface_down.example.json `
  --transport ensp-console `
  --devices config/ensp_console.local.json `
  --fault-type INTERFACE_DOWN `
  --trials 1 `
  --output "reports/live/console_interface_down_${runTag}_trial.json" `
  --raw-output-dir "reports/live/console_interface_down_${runTag}_trial_raw"
```

程序关闭 R2 的 GigabitEthernet0/0/1，诊断后自动执行 undo shutdown 并验证恢复。
正确结果应为 `R2 / INTERFACE_DOWN / GigabitEthernet0/0/1`。
需要三次验收时，把 `--trials 1` 改为 `--trials 3`，同时将两个报告路径中的 `_trial` 改为 `_three`。
两种实验应串行运行，不要同时启动。

## 9. 实验失败或中断时的恢复

先确认 Python 实验进程已经退出，再在 R2 的 eNSP 命令窗口执行：

```text
return
system-view
interface GigabitEthernet0/0/1
undo shutdown
quit
ip route-static 192.168.3.0 255.255.255.0 10.0.23.2
return
display interface GigabitEthernet0/0/1
display ip routing-table 192.168.3.1
```

接口应为 UP/UP，目标静态路由应重新出现。
然后在 R1 的窗口执行 `ping 192.168.3.1`，确认收到回复后再开始下一次实验。
finally 可以处理通常的 Python 异常，但强制结束进程、设备掉线或系统断电时，仍必须独立检查恢复状态。

如果 `all_passed=false`，查看每轮的 `error`、`diagnosis`、`recovery` 和 `post_recovery`，不要只看命令有没有显示成功。

## 10. 答辩时如何准确描述

本实验采用本地 Console 接入运行中的 eNSP 设备。
诊断 Agent 使用规则状态机，根据真实命令回显选择后续动作；本流程没有调用大模型。
修改设备配置的是外层实验控制器，诊断 Agent 本身只执行检查命令。
当过滤路由查询为空时，程序回退查询完整路由表，Parser 按目标 IP 匹配路由；空字符串本身不能证明缺路由。
