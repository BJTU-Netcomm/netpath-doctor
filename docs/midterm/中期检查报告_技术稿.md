## 1. 项目简介、目标与范围调整

项目面向网络设备基础连通性故障，研究如何让程序主动执行检查命令，从设备反馈中提取事实，并输出带证据的诊断。长期方向是适配多种模拟器和设备接入方式，逐步扩展诊断策略。为降低集成复杂度，本阶段首先在 Huawei eNSP 三路由器拓扑上完成原型，使用本地 Console 获取真实 VRP 输出，用规则状态机执行确定性的诊断流程。

本阶段现场范围为接口关闭和静态路由缺失两类故障。SSH 远程控制、大模型策略、多模拟器接入及自动启动拓扑列入下一阶段；这不是把长期目标删除，而是先建立可重复评测的基线。是否涉及立项目标变更，应由组长对照原申报书并向导师说明，当前不能据此宣称原项目全部完成。

## 2. 研究内容与实现方案

业务拓扑为 R1—R2—R3，互联网段分别为 10.0.12.0/24 和 10.0.23.0/24；R3 的 LoopBack0 为 192.168.3.1/24。当前实验从 R1 探测该地址，在 R2 注入故障。业务地址与离线案例中的目标地址不同，各自以 scenario 为准。

诊断 Agent 的核心是 `agent/state_machine.py` 中的 DiagnosisStateMachine。它先 ping 目标，失败后 tracert 定位疑似设备，查询路由，再按事实决定是否检查接口和 ARP。动作先由 action_schema 验证只读和必填参数，经 command_mapper 渲染成 VRP 命令，再交给执行器。

LiveExecutor 调用 ENSPConsoleTransport，读取运行中的 eNSP 设备回显；Parser 使用正则表达式、IP 网络匹配等确定性逻辑提取 facts。离线 ReplayExecutor 读取固定 CLI 文件，复用同一 Parser 和状态机。诊断输出包含设备、类型、接口、required_evidence 字符串数组和 action_trace。V1 字段保持兼容。

外层 live_experiment 控制器负责正常检查、故障注入、调用诊断、finally 恢复和恢复后验证。它剥离传给 Agent 的 ground_truth 与 experiment_control。两类受控实验均提供故障前采集的路由事实作为已知基线，因此当前评测属于已知拓扑和可用基线条件下的受控实验，不能称为对未知网络的盲测。

## 4. 遇到的问题及解决办法

空回显与缺路由不能等同：旧 VRP 的过滤查询可能只返回提示符，已增加完整表回退和负例完整性校验。

命令简表与详细回显不同：已有 display ip interface brief 不能直接供 CHECK_INTERFACE 使用，已加入拒绝误用的测试。详细接口三态原文属于后续现场强化材料，正式采集时仍需保存正常、关闭、恢复三种状态。

拓扑运行与程序逻辑验证不同：本机 eNSP 曾受启动环境干扰，现阶段人工启动拓扑、程序控制设备，把自动启动 GUI 留到后续。中期答辩使用已归档的 eNSP、AI 和 Replay 报告作为证据；后续现场保留失败材料，演示异常时使用明确标注的录像或离线回放。

接口关闭可能触发静态路由退出活动表：旧版报告曾把接口故障端点误判为 R3，已修正诊断顺序和端点优先级。当前路由缺失且有本轮故障前出接口记录时，继续查询该接口；物理状态 DOWN 输出 INTERFACE_DOWN，UP/UP 输出 ROUTE_MISSING，解析失败或协议单独 DOWN 请求更多数据。两类实验均采集并提供基线，不依赖预期故障标签。修复已经过构造回归、执行器链路和 Qwen/百炼报告验证；中期现场即时复测不是前置条件。

解析和诊断仍有边界：目前 ARP 判定只支持已实现的格式与规则，不能证明所有“下一跳不可达”的成因；协议单独 DOWN 的情况也未独立归类。当前规则实现写在 Python 状态机中，fault_catalog 用作规则说明和契约，不是自动加载的通用推理引擎。
