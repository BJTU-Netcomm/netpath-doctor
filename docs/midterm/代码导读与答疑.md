# 从一条命令读懂 NetPath-Doctor

代码路径相对于仓库。先按下面顺序读，不要一开始通读传输层。

## 1. 三个词先理解

action 是“下一步要做什么”，比如检查 R2 接口。raw_output 是设备打印出来的文字。facts 是从文字中提取的数据，比如 physical_status=DOWN。Agent 根据 facts 决定下一个 action，因此它有观察—动作—观察的循环；这里的决策来自人写的规则，不依赖大模型。

## 2. 跟踪一次 CHECK_INTERFACE

1. `agent/state_machine.py :: DiagnosisStateMachine.run` 创建 AgentAction，设备为 R2，参数是完整接口名。
2. `agent/action_schema.py :: validate_action` 检查动作是否在目录中、是否只读、参数是否齐全。这是已定义动作接口的限制，不应夸大为任意不可信输入的通用安全隔离。
3. `agent/command_mapper.py :: render_command` 把接口名填进 action_catalog 模板，得到 `display interface GigabitEthernet0/0/1`。
4. `tool_server/live_executor.py :: LiveExecutor.execute` 选设备，调用 transport.send，再将文本连同动作参数交给 Parser。
5. `tool_server/ensp_console_transport.py :: _send_command` 通过本地 socket 发送命令，等提示符。遇分页发送空格继续读取，采集文件通常是去掉首尾命令和提示符后的正文。
6. `parser/huawei_vrp.py :: parse_interface` 匹配 current state 和 Line protocol current state 两行；Administratively Down 归一成 DOWN。它不接受接口简表。
7. Parser 返回字典：success 表示是否读懂文本，facts 表示读出的事实。success=true 并不表示网络正常。
8. 状态机看到 physical_status=DOWN，调用 `_finish_diagnosis` 返回 INTERFACE_DOWN，带设备、接口、字符串证据和动作轨迹。

示例只是解释结构，不作为新实测结果：

```json
{"success":true,"device":"R2","facts":{"interface":"GigabitEthernet0/0/1","physical_status":"DOWN","protocol_status":"DOWN"},"error":null}
```

## 3. 三个文件理解完整实验

`benchmarks/live_experiment.py :: run_route_missing_trial` 先执行故障前 ping 和目标路由快照，再删除路由并验证缺失，然后调用 diagnose。finally 是“无论诊断正常返回还是抛出通常的 Python 异常，都尝试恢复”的结构；它不能应对断电或强杀进程，所以恢复后还要查路由和 ping。

`benchmarks/live_runner.py :: diagnose_live_scenario` 去掉 ground_truth 和 experiment_control，再建立 LiveExecutor 和 DiagnosisStateMachine。Agent 不读取预期故障标签，但知道拓扑映射；两类受控实验均提供故障前路由基线，不能说它完全不知道实验环境。

`benchmarks/runner.py` 运行离线基线和参数化场景，将诊断与 expected_result 比较。它检查结果、证据子串和动作顺序；20/20 不是统计意义上的通用准确率。

## 4. 路由的特殊处理

目标是 192.168.3.1，路由表可能只有 192.168.3.0/24。`parse_route` 使用 ipaddress 判断目标是否在网段中，再选前缀最长的一条；不能只搜索字符串 192.168.3.1。

空过滤查询不等于缺路由。Console 重试后读取完整表。完整表内没有覆盖目标的项，且表头、路由条数等符合已实现的条件，才返回 route_found=false；无法识别的文本保持错误。若 table 截断，却从中直接推断“没有路由”，就会产生假阳性。

## 5. 需要讲准确的细节

- ping 的 reachable=true 表示丢包率小于 100，不等于 0% 丢包。报告时同时给出 packet_loss。
- tracert 最后可达节点用作疑似故障设备是当前启发式规则，不是适用于一切网络的定理。全部星号时尝试查源路由下一跳。
- 解析失败通常返回 NEED_MORE_DATA；受控实验提供有效故障前路由基线时，路由解析失败允许继续检查该出接口。不能概括成“所有失败立即停止”。
- 当前确认无路由且有故障前出接口记录时，会继续检查该接口：物理 DOWN 判接口故障，UP/UP 判路由缺失，解析失败或协议单独 DOWN 请求更多数据。无基线回放仍使用 V1 无路由分支。基线记录表示先前观察，不证明接口现在正常；当前结论要用新回显。
- fault_catalog 是规则说明，当前判定实际写在 state_machine.py。改变 JSON 规则文件不会自动创建新的判定分支。
- 诊断 Agent 只检查；自动恢复是实验控制器恢复预设故障，不是 Agent 自主规划修复方案。
- 模拟器内 VRP 的命令反馈是真实运行结果；物理网络或其他厂商设备的泛化能力尚未证明。

## 6. 答疑练习

问：这和一个固定脚本有什么区别？

答：它根据每次执行得到的事实走不同分支，记录动作和证据，执行器可以替换。当前仍是有限规则系统，贡献在于可解释闭环与可评测工程基线，不宣称具有大模型自主推理能力。

问：创新在哪里？

答：我们把设备命令、结构化事实、诊断动作和评测接口统一起来，并用真实 VRP 回显验证。它是阶段性工程成果；是否具有研究创新，需要后续用规则与模型、不同拓扑和故障上的对照实验来证明。

问：为什么只有一个模拟器？

答：先用 eNSP 形成可靠基线。传输 send 接口与 Parser 解耦为后续适配预留入口，但尚未验证第二个模拟器，不能把可扩展设计当成已完成支持。

问：为什么不是 SSH？

答：当前主演示使用本机 Console，避免远程管理链路成为中期阻塞。项目已有 SSH 相关代码和探索，但本轮不验收 SSH 端到端集成，下阶段再完成。

问：三次成功足够证明稳定吗？

答：只证明当前版本在指定环境下三次重复成功。我们还需要不同拓扑、版本、干扰和失败注入，才能评价更广泛稳定性。

问：为什么没上大模型也叫 Agent？

答：Agent 的核心是根据观察选择动作。当前策略是规则状态机。我们在汇报时明确这一点，把大模型策略当作后续可比较的实现。

问：恢复失败怎么办？

答：保存 recovery.error 和原始回显，不计通过，先停止后续故障实验，按复现指南手工恢复并确认 ping 正常。finally 不是无条件恢复保证。

## 7. 今天的学习顺序

先用 20 分钟读字段与上述 CHECK_INTERFACE 调用链，再用 20 分钟读状态机两个目标分支，再用 20 分钟对照 PPT 大纲复述流程。之后让队友随机问“这条证据从哪来”“是否偷看答案”“恢复是谁做的”，每题控制在 30 秒内回答。
