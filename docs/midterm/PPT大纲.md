## 04 先读懂设备文字，再判断故障

Parser 的 success 表示“解析成功”，不表示“网络正常”

页面要点：

- display interface 提取 physical_status、protocol_status。
- Administratively DOWN 归一为 DOWN；success 表示解析成功。

配图建议：原文和 facts 对照。

素材和边界：原文、解析 facts 和报告路径一一对应；后续可继续补充三态原文。

讲解备注：【30 秒】以接口为例，Parser 从 current state 和 Line protocol 两行提取物理和协议状态，将 Administratively Down 归一成 DOWN，同时保留 administrative_down 证据。空回显不能直接证明故障，例如无路由需要回退完整表并验证条目完整性。字段来源：parser/huawei_vrp.py；真实回显和解析结果见 reports/live/。两类受控实验使用故障前路由基线，这是受控实验的前提。

## 05 两条诊断路径，输出可核对的证据

目标设备：R2 · 目标地址：192.168.3.1

页面要点：

- 当前无路由＋基线出接口 DOWN → INTERFACE_DOWN。
- 当前无路由＋基线出接口 UP/UP → ROUTE_MISSING。
- 无法读懂接口或协议单独 DOWN → NEED_MORE_DATA。

配图建议：路由和接口诊断分支。

素材和边界：两类受控实验均使用采集的故障前路由；无基线的回放保留 V1 行为。

讲解备注：【30 秒】ping 失败后定位疑似设备，再查目标路由。当前路由缺失时，如果有本轮故障前的出接口记录，就继续读接口：物理 DOWN 返回 INTERFACE_DOWN，UP/UP 返回 ROUTE_MISSING，解析失败或协议单独 DOWN 则请求更多数据。两类实验都提供同样的基线，不传预期故障标签。结果保留命令轨迹和证据。来源：DiagnosisStateMachine.run、reports/live/。
