# NetPath-Doctor 浏览器诊断台

## 启动

在仓库根目录双击 `start_diagnosis_console.cmd`，或运行：

```powershell
.\.venv\Scripts\python.exe -m tools.diagnosis_server
```

浏览器打开 `http://127.0.0.1:8767/`。运行过程中保留终端，按 Ctrl+C 停止。
本轮升级使用 8767，避免与之前运行在 8765 / 8766 的旧服务冲突。如果端口已被另一份诊断台占用，请使用已打开的新版页面；需要重新启动时，先在对应终端按 Ctrl+C，或设置 `$env:NETPATH_UI_PORT='8768'` 后再启动。

## 配置百炼 API

1. 点击右上角 **API 设置**。
2. 运行模式选 **真实 API · 百炼模型**。
3. Base URL 填百炼控制台提供的 **OpenAI 兼容模式根地址**，通常以 `/compatible-mode/v1` 结尾，不附加 `/chat/completions`。项目以前使用的工作空间地址见 `config/bailian.example.env`；如工作空间已变更，以控制台为准。
4. 文字模型 ID 填实际可调用的部署 ID。历史配置为 `qwen3.8-27b`，程序不会假设这个名称必然在当前工作空间可用。
5. API Key 粘贴到密码框。留空会保留本次进程已有的密钥。
6. 可选填图片模型 ID。上传图片时会优先用它；留空则使用文字模型，该模型必须同时支持 `image_url` 视觉输入。文字 API 检测成功不表示图片能力也通过。
7. 点击 **应用并检测 API 连接**。这会向百炼发出一次小的文字请求，收到有效响应才显示“API 已验证”。请求可能产生少量正常 API 费用。
8. 关闭设置。实时检查请选择 **eNSP 实时诊断**；分析文字/图片请选择 **材料分析**。

## eNSP 实时诊断

调用路径为：网页 → 本地 HTTP 服务 → AIHarness → LiveExecutor → ENSPConsoleTransport → 正在运行的 VRP 路由器。

1. 在 eNSP 打开原来的 R1—R2—R3 拓扑，启动三台设备，等待 CLI 能接收命令。
2. 网页选择 **eNSP 实时诊断**，点击 **检测 eNSP 连接**。程序对三台设备实际执行 `display ip interface brief`，以设备回显判断 Console 是否就绪，不只检查端口。
3. 选择源设备（默认 R1），目标填写 `192.168.3.1`（R3 LoopBack0）。实时模式下文字要求可留空；源设备和目标 IP 以这两个字段为准。
4. 点击 **开始 AI 诊断**。模型从五类注册工具中选择检查，页面同步展示命令、原始回显、解析事实和最终状态。
5. 若当前可达，会显示“本次连通性探测正常”，不会强行生成故障。若不通，则根据取得的路由、接口等证据定位；没有足够事实时会返回 `NEED_MORE_DATA`。
6. 每次运行自动保存到 `reports/ui_live/<运行编号>/report.json`，原始 CLI 在同目录 `raw/`；也能从页面导出 JSON。该目录已加入 Git 忽略。

本机 Console 端口由 `config/ensp_console.local.json` 提供，当前是 R1=2000、R2=2001、R3=2002，主机均为 `127.0.0.1`。端口改变时编辑这个本地文件。缺失时可从 `config/ensp_console.example.json` 复制后修改。

公开的连线/业务接口配置在 `config/diagnosis_topology.json`。拓扑变化时需同步更新，程序只允许检查配置中的业务接口，防止把闲置接口 DOWN 误认为故障。图中节点高亮表示 Console CLI 已响应，不表示其所有链路和业务均正常。

实时模式在拓扑区提供两种预设故障的一键注入和恢复，适合现场演示。**R2 → R3 接口关闭**会关闭 R2 的 `GigabitEthernet0/0/1`；**R2 目标路由缺失**会移除 R2 到 `192.168.3.0/24`、下一跳 `10.0.23.2` 的静态路由。注入前会检查 R1 到目标可达，并确认目标路由及接口符合基线；注入后读取设备状态验证结果。诊断结束后点击 **恢复所选故障**，恢复动作也会等待设备回显确认。故障注入保持生效，以便随后启动诊断，不会在诊断完成后自动恢复。服务重启后若仍有故障，可选择对应类型再次点击恢复。

网页不提供任意命令输入。按钮只会执行上述固定配置命令；操作期间诊断和设备预检会互斥。运行时避免同时在 eNSP 自带 Console 窗口输入命令，以免共用同一 Console 造成回显混杂。若注入或恢复未能确认设备状态，请检查页面轨迹和 eNSP CLI，再决定是否继续演示。

老版本 VRP 的 ARP 观察由网页适配层实际执行 `display arp`，Parser 再根据工具参数 `target_ip` 从完整表中筛选，工具语义仍是“检查指定 IP 的 ARP”。页面显示实际命令，报告同时保留请求模板命令。完整表没有目标项时，必须有表头和 Total 结尾才可认定缺失，截断输出不会被当作“没有 ARP”。

结果会保留每次目标 ping 的丢包率；目标可达但有丢包时不表示“完全无丢包”。

“记住到本机配置文件”默认不勾选，仅在服务内存保留配置；勾选后保存到 `config/diagnosis_ui.local.json`，该文件及临时文件已加入 Git 忽略。网页响应不返回密钥，程序不把请求正文写入日志；浏览器不使用 localStorage 保存密钥。凭据字段关闭后会清空。

也支持服务启动时读取 `DASHSCOPE_API_KEY`、`DASHSCOPE_BASE_URL`、`DASHSCOPE_MODEL`、`DASHSCOPE_VISION_MODEL`、`DASHSCOPE_TIMEOUT_SECONDS` 环境变量，或 `config/bailian.local.env` / `.env` 中同名配置。网页本地保存的配置优先于上述启动默认值；要重新使用环境配置，可在服务停止后移走本地 JSON 配置文件。

## 录制实时诊断视频

1. 录屏前启动 eNSP，配置好百炼，完成“检测 eNSP 连接”。
2. 浏览器最大化，选择实时模式；源 R1、目标 `192.168.3.1`。
3. 输入 `检查当前连通性；如果正常如实报告，如果异常请依据设备回显定位。`
4. 开始诊断，展示右侧模型/工具事件，然后展开真实 CLI 回显和结果卡片。
5. 导出 JSON 作为录屏配套记录。实际等待时间取决于 API 和设备响应，可在视频剪辑时加速等待片段并说明。

录制故障诊断需要另按已经验证的实验流程准备实际故障；网页本身不会制造故障。一个健康网络上的正常结果也是有效的现场接入验证。

## 录制材料分析视频

1. 录屏前配置并检测 API，关闭设置窗口，避免在视频中展示凭据。
2. 浏览器最大化，可按 F11 全屏。建议在 1280×720 或更高分辨率录制。
3. 切换为 **材料分析**，输入：`这是一张历史示例截图，浏览器提示无法连接 192.168.56.101:8090。请分析图片中的现象，不要假设它是当前网络状态。`
4. 拖入相应连接失败截图，或粘贴截图（Ctrl+V）。确认缩略图展示的是正确图片。
5. 点击 **开始 AI 诊断**。右侧显示后端实际发生的受理、输入准备、API 等待、响应解析事件；等待期间显示计时。它不是模型内部推理过程，也不虚构实时工具调用。
6. 模型返回后展示“已观察事实 / 可能原因 / 下一步检查”。下方显示本次模型、耗时和调用模式。
7. 可点击 **导出诊断 JSON** 留下记录。下载内容是诊断结果，不包含密钥或上传图片。

**材料分析模式**仅分析输入，不调用设备；**eNSP 实时诊断模式**调用现有 Harness 和 Console 取得事实。录屏时明确本次使用哪个模式，只有实时模式产生的实际工具回显才能作为实时设备检查证据。两个模式均不自动修复网络。

## 本地示例与异常处理

设置中可选 **本地 DEMO · 固定示例**。页面和导出结果都会明确标注 DEMO；该模式不会向模型发请求，也不会识别任意图片。要录制真实模型能力，应切回 API 模式并检测连接。API 出错时程序会报错，不自动回退到固定示例。

- 认证失败 / 权限不足：检查密钥和工作空间地址是否匹配。
- 接口或模型不存在：检查兼容模式 Base URL 与模型 ID。
- 图片调用失败：检查当前模型是否支持视觉输入，必要时配置图片模型 ID。
- 超时：重试；可在环境变量中设置 `DASHSCOPE_TIMEOUT_SECONDS`（1～300 秒）。
- 无有效结构化结果 / 输出过长：简化问题后重试。

## 开发验证

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

`tests/test_diagnosis_console.py` 启动本地 HTTP 模型替身，实际通过 `BailianClient` 验证认证头、文字/图片请求、模型选择、连接检测、进度输出、失败行为和密钥不回显。它验证协议和程序流程，不证明外部百炼账号或真实图片模型可用。

## 答辩展示界面（2026-10-22 更新）

页面采用科研控制台布局，展示 LLM → Harness → eNSP 的架构示意、三节点实验拓扑、诊断执行阶段和可追溯的设备证据。模型轮次、实际工具调用数及耗时由本轮事件与最终报告更新；连接检测不计入诊断工具调用数。运行时的动效用于标识执行阶段，架构图中的连线不代表额外的实时网络测量。节点亮起只代表 Console 响应。

录屏建议使用桌面浏览器最大化，按 F11 进入全屏，保留 100% 页面缩放。先展示架构与任务配置，启动诊断后展示执行轨迹，再滚动展示诊断结论及真实回显。刷新页面会清空当前界面记录，历史报告仍保存在 reports/ui_live 中。
